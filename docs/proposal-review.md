**외대 개인 맞춤 학사 챗봇 기획서 검토 — 2026.11.06**

검토 대상은 `docs/proposal.md`야. 공모전 공개 요강, 기획서에 적힌 학사정보·공지 원문, 훕또기의 공개 화면과 릴리즈노트를 대조했어. 사용자 설명에 따라 서비스의 중심을 **처음 등록한 학생 정보를 계속 활용해 질문마다 개인에게 맞는 답을 주는 챗봇**으로 해석했어. 원본 기획서는 수정하지 않았어.

주제는 유지할 만해. 외대는 입학년도·캠퍼스·전공·이수 유형에 따라 적용되는 규정이 달라서, 개인 프로필을 지속적으로 반영하는 학사 상담이라는 문제 설정이 구체적이야. 다만 지금 문서는 타임라인·알림 서비스를 중심으로 쓰여 있고 챗봇은 확장 기능이어서, 네가 설명한 핵심이 심사위원에게 전달되기 어려워. 제일 먼저 바꿀 건 기능 추가가 아니라 **서비스 정의와 구현 우선순위**야.

**기존 훕또기와의 차이를 정확히 쓰는 방법**

네가 설명한 의도는 분명해. 사용자가 자기 조건을 처음 한 번 등록하고, 이후 질문할 때 그 정보를 반복해서 설명하지 않아도 되는 거야. 답변도 일반 공지를 보여주는 수준에서 끝나지 않고, 그 조건에 해당하는 규정과 필요한 행동으로 좁혀져야 해.

다만 비교문에 “훕또기는 개인화를 전혀 제공하지 않는다”고 쓰면 곤란해. 공개 화면과 릴리즈노트에 맞춤 장학금 찾기, 조건별 판정, 공지 마감 D-day 안내가 확인돼. 맞춤 장학금 입력 조건은 저장하지 않는다고 안내하고 있어. 따라서 **개인화 기능의 유무**보다 **프로필을 저장해 여러 학사 질문에 지속적으로 재사용하는 범위와 경험**을 비교하는 게 정확해. 훕또기의 비공개 내부 기능까지 조사한 것은 아니므로, 공개 화면에서 확인한 범위로 표현해야 해. **기획서에 넣을 서비스 정의와 핵심 기능 제안**

서비스명은 ‘외대 놓침방지’를 유지해도 돼. 부제를 **“내 정보를 기억하는 개인 맞춤 학사 챗봇”**으로 바꾸면 의도가 바로 전달돼.

아래 문단은 제출용으로 다듬어 쓸 수 있어.

> 사용자가 입학년도, 캠퍼스, 학과, 이수학기와 전공 이수 유형을 처음 등록하면, 이후 질문마다 해당 정보를 반영하여 개인에게 적용되는 학사 규정과 필요한 절차를 안내하는 한국외대 맞춤 학사 챗봇이다. 동일한 질문에도 학생별 적용 규정에 따라 답변과 근거를 달리 제공하며, 판단에 필요한 정보가 부족하거나 공식 자료가 충돌하면 추가 질문 또는 담당 부서 확인으로 연결한다.

본선 핵심 기능은 다음 네 가지가 적당해.

1. **프로필 등록·저장·수정**: 입학년도, 캠퍼스, 학과, 현재 이수학기, 학적 상태, 전공 이수 유형을 저장해. 첫 학년에는 전공 유형이 미정일 수 있으니 ‘미정’도 허용해. 학번 전체는 필요하지 않아.
2. **프로필을 반영한 학사 Q&A**: 질문에 관련된 개인 조건과 공식 자료를 함께 사용해서 답변해. 단순히 답변 첫 문장에 학과명을 붙이는 개인화로 끝나면 안 돼.
3. **적용 이유와 출처 표시**: 답변에 ‘어떤 개인 조건을 적용했는지’, 관련 규정, 원문 링크, 확인 기준일을 보여줘. 신청 기간과 방법은 가능한 경우 함께 안내해.
4. **부족한 정보 확인·예외 처리**: 이수학점이나 편입 여부가 있어야 판단할 수 있으면 그때 물어봐. 조건 미확인·규정 충돌을 신청 불가로 처리하거나 추측으로 메우면 안 돼.

프로필을 어디까지 유지하는지도 약속해야 해. 본선에서는 같은 브라우저에서 재접속했을 때 프로필을 다시 쓰는 수준으로 제한할 수 있고, 계정 기반 저장을 선택한다면 사용자별 데이터 분리를 구현해야 해. 기기 간 동기화까지 구현하지 않으면 그 기능을 약속하지 마.

개인 일정·D-day 푸시·4년 로드맵·졸업 진행률·행사 추천·펫은 후속 기능으로 줄이는 게 맞아. 일정 기능을 남긴다면 챗봇이 안내한 신청 기간을 저장하는 정도부터 시작해.

**개인화가 실제로 작동한다는 걸 보여줄 시연**

같은 질문을 서로 다른 프로필에서 보여주는 게 가장 직관적이야.

| 질문 | 프로필 | 기대되는 답변의 차이 |
|---|---|---|
| “졸업하려면 총 몇 학점 필요해?” | 서울캠퍼스 2026학번, 비사범대, 이중전공 | 해당 배분표의 총 126학점을 안내 |
| 같은 질문 | 서울캠퍼스 2024학번, 사범대·AI융합대학을 제외한 대학, 이중전공 | 해당 배분표의 총 134학점을 안내 |

| “이중전공 신청 언제야?” | 2026-2학기가 두 번째 학기인 일반 신입학 재학생 | 해당 학기 일반 신청 대상 조건과 신청 기간을 안내 |

126·134학점은 모든 학생에게 동일하게 적용되는 수치가 아니야. 위 표에 적힌 캠퍼스·입학년도·대학·이수 유형 조건에서 비교해야 해. 졸업학점 총량 안내와 실제 졸업 가능 판정도 구분해야 해. [공식 졸업학점 배분표](https://www.hufs.ac.kr/hufs/11373/subview.do)

프로필 저장의 차별성은 첫 질문 다음에 더 잘 보여. 첫 질문에 답한 뒤 “그럼 부전공으로 바꾸면?”, “신청은 어디서 해?”라고 이어 물어도 사용자 조건과 대화 주제가 유지되는 장면을 보여줘. 답변에 필요하지 않은 조건을 매번 다시 묻지 않는지가 중요해.

| 교내 FLEX 졸업시험 | 해당 공고는 지정 언어와 사전 신청한 해당 학과 재학생을 대상으로 해 | 모든 4학년의 공통 필수 일정처럼 표시하지 마 |
| 졸업논문·시험 보고서 마감 | 학사일정에 적힌 마감은 성적보고서·심사보고서 제출 마감이야 | 학생의 학과별 논문 제출일·시험 신청일과 같다고 간주하지 마 |

특히 학점 충돌은 네 서비스의 필요성과 난이도를 동시에 보여줘. 출처가 있다는 이유만으로 정답이 확정되는 건 아니라는 실제 사례거든. 씨발, 여기서 AI가 자신 있게 한쪽을 찍어주면 개인 맞춤이라는 강점이 바로 불신으로 돌아와.

**AI 활용 계획은 이렇게 구체화해**

아래 흐름이면 생성형 AI를 사용하는 이유와 통제 방식이 함께 드러나.

`질문 + 저장 프로필 → 질문에 필요한 조건 확인 → 개인 조건에 맞는 공식 자료 검색 → 검증된 규정과 예외 대조 → 개인화 답변 + 적용 조건 + 출처`

- 공식 자료에는 입학년도 범위, 캠퍼스, 적용 학과·대학, 학기, 시행 시점과 원문 링크를 붙여. 학년만으로 검색 범위를 고정하면 편입·휴복학 사례에서 틀릴 수 있어.
- 명확한 학점 계산과 자격 조건은 검증된 데이터와 로직으로 처리하고, AI는 질문 해석·관련 근거 연결·설명 생성에 활용해. AI가 졸업요건 수치를 새로 만들어내게 두지 마.
- 관련 문서끼리 충돌하면 단정적인 개인 판정을 보류하고 충돌 내용과 문의할 부서를 안내해. 최신 게시일이라는 이유만으로 무조건 덮어쓰는 것도 피해야 해.
- 사용자가 이번 질문에 제시한 가정 조건은 답변에 반영하되, 저장 프로필 수정은 별도 동작으로 구분해. 타인의 조건이나 가정 질문이 사용자 정보로 남으면 후속 답변이 꼬여.
- 학점·평점·인증 현황은 기본 프로필만으로 알 수 없어. 실제 필요한 질문에서 추가 입력받고, 미입력 상태에서는 확인 가능한 범위까지만 답해.
- 공지 원문이 바뀌면 검색 자료와 규정 데이터를 갱신할 절차가 있어야 해. 본선에서는 개발자가 직접 검수하는 작은 운영 범위부터 잡아.

바이브코딩 부분은 지금처럼 도구명만 쓰는 것보다 **요구사항 프롬프트 → 생성 코드 검토 → 오류 발견 → 수정·검증**의 실제 예시를 결과보고서에 남기겠다고 보완하면 좋아. 공모전 공개 요강에서 개발 로그 제출을 필수라고 확인한 것은 아니고, 개발 방식을 설득력 있게 보여주기 위한 제안이야.

**1인·3주 구현 범위와 검증**

핵심 주제는 입학년도별 졸업학점, 이중전공 신청, 휴·복학 정도의 2~3개 영역부터 잡아. 지원 프로필 범위와 미지원 예외도 명시해. 전체 학과의 졸업 판정까지 약속하면 학사 데이터 검수가 존나 커져.

| 기간 | 결과물 | 완료 기준 |
|---|---|---|
| 1주차 11/16~22 | 프로필 저장·수정, 검증한 학사 자료, 기본 RAG 질의응답 | 재접속 후 프로필을 재사용하고 두 프로필의 같은 질문에 적용 규정이 달라짐 |
| 2주차 11/23~29 | 질문별 조건 반영, 추가 질문, 근거·예외 표시 | 편입생·정보 누락·문서 충돌·임시 조건 사례를 처리 |

다음 수치는 **이미 달성한 성과가 아니라 제안하는 목표**야. 개발 중 검증 결과를 보고 확정해야 해.

짧은 시험으로 증명할 수 있는 건 질문 해결 속도와 개인 조건 적용 품질이야. 졸업률 향상·행정 문의 감소는 장기 기대효과로 써야 해. 사용자 만족도만 조사하면 정확한 상담인지 검증이 빠져.

**원본의 나머지 문장을 다듬을 부분**

- 26행의 ‘대학 생활 전체를 좌우하는 결정을 1주일 안에 내려야 한다’는 표현은 신청 기간과 사전 탐색 기간을 혼동시켜. ‘신청 시기를 놓치면 이후 선택 기회가 여석에 제한된다’가 더 정확해.
- 46행의 ‘4년 흐름으로 안내해 주는 창구는 없다’는 단정은 전체 서비스 조사가 더 필요해. 개인 조건을 계속 대조해야 하는 부담을 중심으로 설명해.
- 35행의 창업장학금·HUFS Dream 장학금 사례는 부록에 각각의 공고 링크를 추가해. 현재 부록만으로 두 사례의 근거를 모두 따라갈 수는 없어.
- 126행의 31학점 예시는 입력 경로가 없고 34·32학점 충돌도 얽혀 있어. 프로필별 졸업학점 답변 예시로 바꾸는 편이 훨씬 명료해.
- 학교 앱과 별도로 PWA 푸시까지 유지한다면 지원 기기·사용자 알림 허용·iOS 홈 화면 추가 등의 조건을 구현 계획에 반영해야 해. 홈 화면에 추가하는 것만으로 알림 권한이 자동으로 생기지는 않아. [WebKit 공식 Web Push 안내](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- 예상 사용자 규모는 ‘전체 재학생’ 외에 본선 시험 참여자 수, 모집할 캠퍼스·학과와 첫 적용 대상을 구체화해. 근거 없는 전체 수요 추정치는 만들지 마.
- 개인정보 항목은 학번·실명뿐 아니라 저장할 프로필, 추가 성적정보, 대화 기록의 저장 위치·삭제 방법까지 실제 구현 범위에 맞게 설명해.
